# Система самообслуживания для ресторана

Техническая документация · версия 0.1 (черновик) · 24 ноября 2026

## 1. Назначение и границы проекта

### 1.1. Цель

Локальная система приёма заказов для ресторана. Гость сам оформляет заказ на планшете-киоске и платит картой через платёжный терминал. После подтверждения оплаты заказ автоматически раскладывается по станциям (кухня, гриль, закуски) с учётом времени приготовления каждой части. Система работает без интернета и синхронизируется с существующим веб-приложением, когда связь появляется.

### 1.2. Что входит в версию 1

- киоски самообслуживания, экраны станций, экран выдачи и панель оператора;
- локальный сервер с бизнес-логикой и базой данных;
- интеграция с платёжным терминалом;
- меню с модификаторами, которое редактирует оператор;
- программа лояльности с персональными QR-кодами гостей;
- двусторонняя синхронизация с облачным веб-приложением.

### 1.3. Что не входит

- мобильное приложение гостя (QR можно показать с любого телефона или карты);
- онлайн-заказы и доставка;
- складской учёт и технологические карты с ингредиентами;
- фискализация и бухгалтерия: требования зависят от страны, интеграция с кассовым ПО вынесена в отдельный этап;
- несколько ресторанов на одном локальном сервере (рестораны различаются только в облаке, по `restaurant_id`).

### 1.4. Глоссарий

| Термин | Значение |
| --- | --- |
| Киоск | Планшет в зале, на котором гость сам делает заказ |
| Станция | Зона приготовления (кухня, гриль, закуски) со своим экраном |
| Задача станции | Часть заказа для одной станции (`station_task`) |
| Выдача | Экран с номерами готовых заказов |
| Оператор | Сотрудник, который редактирует меню и разбирает спорные платежи |
| Outbox | Очередь изменений, которые ещё не отправлены в облако |
| Эквайер | Банк, который обрабатывает карточные платежи |

## 2. Требования

### 2.1. Функциональные

| ID | Требование |
| --- | --- |
| FR-1 | Гость собирает заказ из меню с модификаторами и комментарием |

| FR-3 | Гость может применить скидку, показав свой QR-код |

| FR-12 | Синхронизация меню, гостей, заказов и платежей с облачным веб-приложением |

### 2.2. Нефункциональные

| Область | Требование |
| --- | --- |
| Автономность | Без интернета работает всё, кроме синхронизации. Оплата зависит только от канала самого терминала к банку |
| Задержка | Заказ появляется на станции не позже 1 секунды после подтверждения оплаты |
| Нагрузка (допущение) | До 6 киосков, 4 экрана станций, до 60 заказов в час в пик. Цифры нужно уточнить у заказчика |
| Устойчивость | После перезапуска сервера или планшета состояние восстанавливается из базы, ни один оплаченный заказ не теряется |
| Резервирование | Копия базы на внешний носитель или в облако не реже раза в час |
| Безопасность | Данные карт не хранятся и не проходят через наш код (требование PCI DSS). Роли и PIN-вход |
| Деньги | Суммы хранятся целыми числами в минимальных единицах валюты (копейки, центы) |
| Время | В базе всегда UTC, в интерфейсе часовой пояс ресторана |
| Сопровождение | Миграции схемы (Alembic), версионирование API, структурные логи |

## 3. Архитектура

### 3.1. Общая схема

```
Облако: веб-приложение (API)
        ▲
        │  HTTPS, только когда есть интернет
        │
┌───────┴───────────────────────────────────────────┐
│ Локальный сервер (FastAPI + SQLite)               │
│ заказы · планировщик · оплата · лояльность · меню │
│ sync-воркер · WebSocket-шина                      │
└──┬────────┬─────────┬─────────┬─────────┬─────────┘
   │        │         │         │         │
Киоски  Станции   Выдача   Оператор   Терминал
(N шт.) (кухня,   (экран)  (планшет)  (карты, свой
        гриль,                         канал к банку)
        закуски)
```

Все устройства ресторана работают в одной локальной сети. Интернет нужен только серверу и только для синхронизации.

### 3.2. Компоненты

| Компонент | Технологии | Ответственность |
| --- | --- | --- |
| Локальный сервер | Python 3.12, FastAPI, SQLAlchemy 2, Alembic, SQLite (WAL) | Вся бизнес-логика. Единственный источник правды о заказах ресторана |
| Планировщик | Модуль сервера | Расчёт `start_at` и очередей станций |
| Платёжный модуль | Интерфейс `PaymentTerminal` и адаптер под конкретную модель терминала | Запуск платежа, получение результата, сверка статуса |
| Sync-воркер | Фоновая задача asyncio | Отправка outbox в облако, получение изменений меню и гостей |
| Android-приложение | Kotlin, Jetpack Compose, OkHttp, Room, CameraX, ML Kit | Четыре режима: киоск, станция, выдача, оператор |
| Облачное веб-приложение | Уже существует | Хранит меню и гостей централизованно, принимает заказы и платежи для отчётности |

### 3.3. Принципы

1. **Сервер принимает все решения.** Цену, скидку и статусы считает сервер. Клиент только показывает результат, иначе модифицированный клиент сможет отправить любую цену.
2. **Идемпотентность.** Каждый изменяющий запрос несёт UUID, созданный на клиенте. Повторная отправка не создаёт дубль.
3. **Offline-first.** В рабочем потоке нет обязательных обращений в интернет.
4. **Журналы вместо правок.** Заказы, платежи и баллы лояльности только добавляются. Исправление записывается новой записью, а не заменой старой.
5. **UUID везде.** Идентификаторы создаются на месте и не конфликтуют при слиянии с облаком.
6. **Расчёты один раз.** Итоговая сумма и время старта фиксируются в момент оформления и сохраняются в базе.

### 3.4. Почему сервер не на планшете

Python на Android запустить можно (Chaquopy, Termux), но система убивает фоновые процессы, батарея ограничена, а к одному серверу должны подключаться несколько устройств одновременно. Поэтому сервер вынесен на отдельное устройство ресторана: мини-ПК или Raspberry Pi 5 с SSD. SSD нужен, потому что SD-карты быстро выходят из строя при частой записи.

### 3.5. Сеть

- Отдельная сеть (VLAN или SSID) для устройств системы. Гости к ней не подключаются.
- У сервера статический IP и локальное имя (например, `pos.local`).
- Киоски по возможности подключаются по Ethernet (PoE), станции и выдача по Wi-Fi.
- Соединение с сервером защищено TLS. Сертификат выдаётся собственным центром сертификации ресторана и устанавливается на планшеты при настройке.
- Терминал находится в той же сети, но к банку ходит по собственному каналу (SIM или LTE). Тогда падение интернета ресторана не останавливает оплату.
- Сервер подключён к ИБП, иначе отключение электричества может повредить базу.

## 4. Android-приложение

### 4.1. Один APK, четыре режима

Приложение одно. Роль устройства (`device.role`) назначает оператор при регистрации, после чего приложение само открывает нужный интерфейс.

| Режим | Где стоит | Что делает |
| --- | --- | --- |
| Киоск | В зале | Заказ, QR-скидка, запуск оплаты |
| Станция | Кухня, гриль, закуски | Очередь задач, таймеры, смена статусов |
| Выдача | Над стойкой выдачи | Номера готовых заказов |
| Оператор | У управляющего | Меню, гости, платежи, устройства, отчёты |

### 4.2. Киоск

Сценарий гостя:

1. Приветствие и выбор «в зале» или «с собой».
2. Меню по категориям, карточка блюда с модификаторами.
3. Корзина.
4. Сканирование QR-кода гостя (необязательный шаг).
5. Итоговая сумма и кнопка «Оплатить».
6. Экран «Приложите карту к терминалу».
7. Номер заказа и ожидание.

Требования к киоску:

- **Режим киоска.** Lock Task Mode, приложение назначено Device Owner (настраивается при первичной регистрации планшета). Системные кнопки и шторка заблокированы, приложение запускается само при включении, экран не гаснет.
- **Сброс по бездействию.** Корзина и сессия сбрасываются через 90 секунд без касаний, предупреждение показывается за 15 секунд. Во время оплаты таймер отключён.
- **Кэш меню.** Меню хранится в Room и обновляется по версии. Это нужно, чтобы экран не был пустым при кратком обрыве связи.
- **Нет связи с сервером.** Киоск показывает «Временно недоступно, обратитесь к сотруднику» и заказ не принимает. Принять заказ без сервера нельзя: гость заплатит, а кухня заказ не увидит.
- **Итоговая сумма.** Киоск показывает предварительную сумму, но окончательную всегда присылает сервер.
- **Доступность.** Крупные кнопки, высокий контраст, статус не передаётся только цветом.

### 4.3. Станция

Экран показывает ленту задач, отсортированных по `planned_start_at`. В каждой карточке: номер заказа, блюдо, модификаторы и комментарий, тип заказа (в зале или с собой) и таймер.

| Состояние | Что видит повар |
| --- | --- |
| Ожидает | Серая карточка и таймер «начать через 3:40» |
| Пора начинать | Подсветка и звуковой сигнал |
| Готовится | Таймер до готовности |
| Опаздывает | Красная карточка, если готовность сдвигается |

Повар нажимает «Начал» и «Готово». Станция видит также, что делают остальные станции по этому заказу, чтобы не отдавать часть заказа раньше времени. Обновления приходят по WebSocket, а после потери связи экран запрашивает актуальный список.

### 4.4. Выдача

Два столбца: «Готовится» и «Готово». Номер переходит в «Готово», когда все задачи заказа получили статус `ready`. Номер сопровождается звуковым сигналом. После выдачи сотрудник отмечает заказ выданным, либо номер исчезает сам через заданное время (настройка). Тот же APK можно запустить на Android-телевизоре.

### 4.5. Оператор

Вход по PIN. Разделы:

- **Меню:** категории, блюда, цены, модификаторы, привязка блюд к станциям и время приготовления.
- **Гости:** карточки, скидки, выпуск и отзыв QR.
- **Платежи:** список платежей, отдельная очередь неопределённых, возвраты.
- **Устройства:** регистрация, роли, состояние связи, версия приложения.
- **Отчёты и журнал действий.**

Правки меню применяются сразу и попадают на киоски по версии. Изменение цены не влияет на уже созданные заказы, потому что цена копируется в строку заказа при оформлении.

## 5. База данных

### 5.1. Общие правила

- СУБД: SQLite в режиме WAL с `foreign_keys=ON` и `synchronous=FULL`. Режим FULL выбран из-за платежей: после отключения питания не должно пропасть подтверждение оплаты. Для одного ресторана производительности хватает, при росте переход на PostgreSQL выполняется через SQLAlchemy и Alembic.
- Первичные ключи: UUID (лучше UUIDv7, он сортируется по времени). Идентификаторы создаются там, где возникла запись.
- Суммы: целые числа в минимальных единицах валюты. Тип `float` для денег не используется.
- Время: UTC, тип `timestamp`.
- Перечисления хранятся в `text` с ограничением `CHECK`.
- Служебные поля (СП) есть у справочников, которые синхронизируются: `version int`, `created_at`, `updated_at`, `deleted_at` (мягкое удаление).
- `version` — оптимистичная конкурентность и конфликты синхронизации записи. Курсор инкрементального меню — отдельное поле `revision` (см. ниже).
- Журнальные таблицы (`payment`, `loyalty_tx`, `audit_log`) не обновляются и не удаляются, кроме явно отмеченных полей статуса.

### 5.2. Группы таблиц

| Группа | Таблицы |
| --- | --- |
| Меню | `category`, `menu_item`, `modifier_group`, `modifier`, `menu_item_modifier_group` |
| Станции | `station`, `item_station`, `station_task` |
| Заказы | `orders`, `order_line`, `order_line_modifier` |
| Оплата | `payment`, `refund`, `terminal` |
| Гости и лояльность | `guest`, `guest_lock`, `loyalty_tx`, `qr_scan_log` |
| Устройства и персонал | `device`, `device_registration_code`, `staff`, `audit_log` |
| Синхронизация | `sync_outbox`, `sync_state`, `idempotency_key` |

### 5.3. Меню

```sql
-- Глобальная монотонная ревизия меню хранится в sync_state (key = 'menu_revision').
-- При любом изменении меню-таблиц в той же транзакции счётчик увеличивается;
-- затронутая запись получает revision = новое значение.
-- Изменение item_station / menu_item_modifier_group также обновляет revision блюда.
-- GET /menu?since=N возвращает записи с revision > N (включая soft-deleted) и текущую revision.

category (
  id uuid pk, name text not null, sort_order int default 0,
  active bool default true, revision int not null default 0, СП
)

menu_item (
  id uuid pk, category_id uuid fk category, name text not null,
  description text, price int not null check (price >= 0),
  image_path text, active bool default true,
  available_from time null, available_to time null,   -- окно продаж (завтраки и т. п.)
  updated_by uuid fk staff, revision int not null default 0, СП
)

modifier_group (
  id uuid pk, name text not null,                      -- «Прожарка», «Добавки»
  min_select int default 0, max_select int default 1,
  revision int not null default 0, СП
)

modifier (
  id uuid pk, group_id uuid fk modifier_group, name text not null,
  price_delta int default 0, active bool default true,
  revision int not null default 0, СП
)

menu_item_modifier_group (
  item_id uuid fk, group_id uuid fk, primary key (item_id, group_id)
)
```

### 5.4. Станции и время приготовления

Связь блюда со станциями вынесена в отдельную таблицу: у одного блюда может быть несколько этапов в разных зонах, и у каждого этапа своё время.

```sql
station (
  id uuid pk, code text unique not null,               -- kitchen, grill, cold
  name text not null,
  capacity int not null default 1,                     -- сколько задач станция ведёт одновременно
  active bool default true, СП
)

item_station (
  id uuid pk, item_id uuid fk menu_item, station_id uuid fk station,
  step_name text not null,                             -- «Стейк», «Гарнир», «Соус»
  prep_seconds int not null check (prep_seconds > 0),
  unique (item_id, station_id, step_name),
  revision int not null default 0, СП
)
```

Пример. Блюдо «Стейк с картофелем и соусом» имеет три записи: гриль, 720 секунд; кухня, 360 секунд; закуски, 120 секунд. Всё блюдо готово, когда готовы все три этапа.

### 5.5. Заказы

```sql
orders (
  id uuid pk,                                          -- создаёт киоск, защита от дублей
  business_date date not null, seq int not null,       -- номер выдаёт сервер
  number text not null,                                -- A-017, сбрасывается каждый день
  kiosk_id uuid fk device, type text check (type in ('dine_in','takeaway')),
  status text not null,                                -- см. раздел 6
  guest_id uuid fk guest null,
  discount_percent int default 0,                      -- копия скидки на момент заказа
  subtotal int, discount_total int, total int,
  created_at, paid_at, ready_at, completed_at, cancelled_at, updated_at,
  unique (business_date, seq)
)

order_line (
  id uuid pk, order_id uuid fk orders, item_id uuid fk menu_item,
  item_name text, unit_price int,                      -- копия на момент заказа
  qty int check (qty > 0), comment text, line_total int
)

order_line_modifier (
  id uuid pk, order_line_id uuid fk order_line,
  modifier_id uuid fk modifier, name text, price_delta int
)

station_task (
  id uuid pk, order_id uuid fk orders, order_line_id uuid fk order_line,
  station_id uuid fk station, step_name text,
  prep_seconds int,                                    -- копия item_station на момент заказа
  planned_start_at timestamp, planned_ready_at timestamp,
  started_at timestamp null, ready_at timestamp null,
  status text check (status in ('planned','cooking','ready','cancelled')),
  updated_at
)
```

Названия, цены и время приготовления копируются в строки заказа. Это защищает историю от правок меню: оператор может изменить цену или время, но старые заказы не изменятся.

### 5.6. Оплата

```sql
terminal (
  id uuid pk, name text, model text,
  protocol text,                                       -- zvt | opi | vendor_sdk
  host text, port int,
  kiosk_id uuid fk device null,                        -- заполняется, если терминал привязан к киоску
  active bool default true, last_seen_at timestamp
)

payment (
  id uuid pk, order_id uuid fk orders, attempt int not null,
  amount int not null, currency char(3) not null,
  status text check (status in ('created','in_progress','approved',
                                'declined','cancelled','unknown','refunded')),
  terminal_id uuid fk terminal,
  idempotency_key uuid unique not null,
  reference text unique not null,                      -- уходит в терминал, по нему ищем транзакцию
  provider_txn_id text, auth_code text, rrn text,
  card_last4 char(4), card_scheme text,
  error_code text, raw_response json,
  created_at timestamp, finished_at timestamp null,
  resolved_by uuid fk staff null, resolution_note text
)

-- у заказа не может быть двух активных попыток оплаты сразу
create unique index uq_payment_active on payment(order_id)
  where status in ('created','in_progress','unknown');

refund (
```

## 6. Жизненный цикл заказа

### 6.1. Статусы заказа

```
awaiting_payment → paid → in_progress → ready → completed
       │             │
       │             └→ refunded (только через возврат)
       └→ cancelled
```

Корзина существует только на киоске. Заказ создаётся на сервере в момент нажатия «Оплатить», сразу в статусе `awaiting_payment`.

| Статус | Значение | Кто переводит |
| --- | --- | --- |
| `awaiting_payment` | Состав и сумма зафиксированы, ждём оплату | Сервер при создании |
| `paid` | Платёж подтверждён, задачи созданы | Сервер при `approved` |
| `in_progress` | Хотя бы одна задача в работе | Сервер, когда повар нажал «Начал» |
| `ready` | Все задачи готовы | Сервер автоматически |
| `completed` | Заказ выдан гостю | Сотрудник на выдаче |
| `cancelled` | Отменён до оплаты | Сервер по таймауту или оператор |
| `refunded` | Оплата возвращена | Оператор через возврат |

### 6.2. Статусы платежа

```
created → in_progress → approved → refunded
                     ↘ declined
                     ↘ cancelled
                     ↘ unknown → (approved | declined)  // решает оператор или сверка с терминалом
```

### 6.3. Правила переходов

- Состав заказа после создания не меняется. Чтобы изменить заказ до оплаты, киоск отменяет старый и создаёт новый.
- Задачи станций создаются только после `approved`, и только в одной транзакции с изменением статуса платежа и заказа.
- Статус `ready` сервер выставляет сам, когда все задачи заказа имеют статус `ready` (отменённые не учитываются).
- Заказ в `awaiting_payment`, по которому платёж не начат в течение 5 минут, отменяется автоматически, а QR гостя освобождается.
- Заказ с платежом в `unknown` автоматически не отменяется, пока оператор не разберёт платёж.
- Отмена оплаченного заказа возможна только оператором: сначала возврат через терминал, потом отмена задач на станциях.

### 6.4. Последовательность оплаты

1. Киоск отправляет `POST /orders` с UUID заказа, строками и QR-токеном (если был).
2. Сервер проверяет доступность блюд, считает суммы и скидку, блокирует QR, присваивает номер и возвращает итог.
3. Киоск вызывает `POST /orders/{id}/payments`. Сервер создаёт платёж в статусе `created` и передаёт терминалу команду на списание с `reference`.
4. Платёж переходит в `in_progress`, киоск показывает «Приложите карту».
5. Терминал возвращает результат. Сервер при `approved` **в одной транзакции** меняет статус платежа и заказа, создаёт и планирует `station_task`, начисляет баллы, закрывает блокировку QR и пишет записи в `sync_outbox`.
6. Сервер рассылает события по WebSocket: станциям (новые задачи), киоску (результат), экрану выдачи (номер в списке «Готовится»).
7. При `declined` или `cancelled` платёж закрывается, заказ остаётся в `awaiting_payment`, гость может повторить попытку (новый `attempt` и новый `idempotency_key`).
8. Если результат неизвестен (обрыв связи, зависание терминала), действует процедура из раздела 8.

## 7. Планирование приготовления

### 7.1. Идея

Все части заказа должны быть готовы одновременно. Долгие этапы стартуют сразу, короткие откладываются. Дополнительно планировщик учитывает загрузку станций: если гриль занят следующие 8 минут, новое блюдо на нём начнётся не раньше.

У станции есть `capacity`: сколько задач она ведёт одновременно. Внутри планировщика станция представлена набором слотов, у каждого слота есть время, когда он освободится (`free_at`). Состояние слотов хранится в памяти сервера и восстанавливается при запуске из задач со статусами `planned` и `cooking`.

### 7.2. Алгоритм

Вызывается один раз при переходе заказа в `paid`, внутри той же транзакции.

```python
def plan_order(tasks, stations, now):
    # 1. Пробная раскладка «как можно раньше» на копии состояния станций
    trial = copy.deepcopy(stations)
    chains = defaultdict(list)                # (station_id, slot_index) -> [задачи]
    finish = now
    for t in sorted(tasks, key=lambda t: t.prep_seconds, reverse=True):
        slot = trial[t.station_id].earliest_slot()
        begin = max(now, slot.free_at)
        slot.free_at = begin + timedelta(seconds=t.prep_seconds)
        chains[(t.station_id, slot.index)].append(t)
        finish = max(finish, slot.free_at)

    # 2. Заказ готов в момент finish. Каждую цепочку сдвигаем к этому моменту,
    #    чтобы все задачи закончились одновременно
    for (station_id, idx), chain in chains.items():
        end = finish
        for t in reversed(chain):
            t.planned_ready_at = end
            t.planned_start_at = end - timedelta(seconds=t.prep_seconds)
            end = t.planned_start_at
        stations[station_id].slots[idx].free_at = finish

    return finish                              # плановая готовность заказа
```

Порядок «сначала самые долгие» нужен, чтобы длинные этапы занимали слоты первыми. Сдвиг в конец окна безопасен: он никогда не заходит на время, которое уже занято другими заказами, потому что старт любой цепочки не раньше пробного.

### 7.3. Пример

Заказ из одного блюда «Стейк с картофелем и соусом», все станции свободны:

| Станция | Этап | Длительность | Старт | Готово |
| --- | --- | --- | --- | --- |
| Гриль | Стейк | 12:00 | сразу | 12:00 |
| Кухня | Гарнир | 06:00 | через 6:00 | 12:00 |
| Закуски | Соус | 02:00 | через 10:00 | 12:00 |

На экране кухни карточка гарнира сначала серая с таймером «начать через 6:00», в нужный момент подсвечивается и подаёт сигнал. Гостю после оплаты можно показать ориентировочное время: `finish - now`.

### 7.4. Отставание и пересчёт

- Если повар нажал «Начал» позже плана больше чем на заданный порог (по умолчанию 30 секунд), сервер пересчитывает **только ещё не начатые** задачи этого заказа: их старты сдвигаются так, чтобы они закончились вместе с отстающей.
- Задачи в работе (`cooking`) и готовые не трогаются.
- Если станция закончила раньше плана, остальные задачи не ускоряются: горячее должно прийти к моменту, когда готово всё.
- Каждый пересчёт публикуется по WebSocket, чтобы экраны станций и выдачи сразу показали новое время.

### 7.5. Ограничения версии 1 и развитие

- Свободные «окна» внутри слота станции не заполняются задачами других заказов. Алгоритм получается консервативным, но простым и предсказуемым.
- Время приготовления берётся из `item_station` как константа. В следующей версии можно уточнять его по фактическим данным (разница между `started_at` и `ready_at`).
- Курсы подачи (сначала закуски, потом основное) и приоритет заказов «с собой» не поддерживаются и добавляются отдельной задачей.
- Если оператор отключил станцию (например, гриль сломан), блюда с обязательным этапом на этой станции становятся недоступными на киосках.

## 8. Оплата и платёжный терминал

### 8.1. Требования к терминалу

- Локальный протокол или SDK (ZVT, OPI, Adyen local Terminal API, SDK производителя). Облачные терминалы, которые работают только через интернет провайдера, не подходят: при пропадании интернета оплата остановится.
- Собственный канал к банку (SIM или LTE), независимый от интернета ресторана.
- Запрос статуса транзакции по `reference`. Без него нельзя безопасно разбирать неопределённые платежи.
- Возврат и отмена, закрытие смены с отчётом.
- Режим офлайн-авторизации (принять платёж без связи с банком) **выключен**: риск отказа банка в этом случае ложится на ресторан.

### 8.2. Способы подключения

|  | Вариант A: терминал привязан к киоску | Вариант B: терминалом управляет сервер |
| --- | --- | --- |
| Связь | USB, Bluetooth или SDK на планшете | Терминал в локальной сети |
| Кто шлёт команды | Киоск | Сервер |
| Источник правды об оплате | Киоск, потом сообщает серверу | Сервер |
| Если киоск завис | Состояние платежа неизвестно | Сервер доведёт платёж до конца и запросит статус |
| Сложность | Ниже | Выше, но надёжнее |

Рекомендуется вариант B, если терминал его поддерживает. Выбор делается по результатам изучения документации выбранной модели.

### 8.3. Интерфейс платёжного модуля

Бизнес-логика не знает о протоколе. Она работает с интерфейсом, под который пишутся адаптеры:

```python
class PaymentTerminal(Protocol):
    async def sale(self, amount: int, currency: str, reference: str) -> TerminalResult: ...
    async def status(self, reference: str) -> TerminalResult: ...
    async def refund(self, provider_txn_id: str, amount: int, reference: str) -> TerminalResult: ...
    async def abort(self) -> None: ...
    async def end_of_day(self) -> SettlementReport: ...
```

`TerminalResult` содержит статус (`approved`, `declined`, `cancelled`, `unknown`), `provider_txn_id`, `auth_code`, `card_last4`, `error_code` и сырой ответ для отладки. Адаптеры: под выбранную модель терминала и `MockTerminal`, который имитирует одобрение, отказ, таймаут и обрыв связи. Без него невозможны автоматические тесты и разработка до получения оборудования.

### 8.4. Неопределённый результат платежа

Связь могла оборваться уже после того, как гость приложил карту, и неизвестно, списаны ли деньги. Процедура:

1. Автоматического повтора нет: повторная команда `sale` может привести к двойному списанию.
2. Сервер запрашивает у терминала статус по `reference` (`status`), несколько попыток с паузой до 60 секунд.
3. Если статус получен, платёж переводится в `approved` или `declined` и обрабатывается как обычно.
4. Если нет, платёж получает статус `unknown`, заказ остаётся замороженным, гостю показывается «Проверяем оплату», затем «Обратитесь к сотруднику» с номером заказа.
5. Платёж попадает в очередь оператора. Оператор сверяет его с чеком или отчётом терминала и вручную выбирает `approved` или `declined`, оставляя комментарий. Решение попадает в `audit_log`.
6. После `approved` по такому платежу выполняется обычная обработка: создаются задачи станций и начисляются баллы.

### 8.5. Возвраты

Возврат выполняет оператор через терминал (refund или reversal, как поддерживает модель). Последовательность: запись в `refund` со статусом `requested`, команда терминалу, при успехе `done`, статус платежа `refunded`, задачи станций заказа в `cancelled`, обратная запись `reversal` в `loyalty_tx`. Если заказ уже готовится, станции получают уведомление об отмене.

### 8.6. Сверка и закрытие смены

В конце дня оператор запускает закрытие смены на терминале (`end_of_day`). Сервер сравнивает сумму платежей `approved` и `refunded` за день с итогом терминала и показывает расхождения. Расхождение это сигнал разобрать платежи, а не повод править данные задним числом.

### 8.7. Чеки и фискализация

Нужен принтер чеков на киоске или на выдаче. Требования к кассовым чекам и фискальным данным зависят от страны и формы бизнеса ресторана. До выбора страны и терминала фискализация считается отдельным модулем (`ReceiptService`) за интерфейсом и в версию 1 не входит.

## 9. Лояльность и QR-коды гостей

### 9.1. Модель

У каждого гостя свой уникальный QR-код. Размер скидки в коде не хранится: он лежит в базе и меняется без перевыпуска кода. Бонусные баллы ведутся журналом `loyalty_tx`, баланс считается суммой записей. Вся проверка выполняется на локальном сервере, поэтому работает без интернета (при условии, что база гостей уже синхронизирована).

### 9.2. Содержимое QR

В QR лежит строка вида `L1.<токен>`, где токен это 128 случайных бит в кодировке base32. Токен не содержит данных о госте и не угадывается. Сервер хранит только SHA-256 от токена (`guest.qr_token_hash`). Поэтому утечка базы не позволяет подделать код, а сам QR отображается только в момент выпуска или перевыпуска (в веб-приложении, письме, Wallet-карте или на печатной карте).

### 9.3. Сканирование на киоске

1. Киоск включает фронтальную камеру (CameraX) и распознаёт код через ML Kit Barcode Scanning. Токен никуда, кроме сервера, не передаётся.
2. Киоск вызывает `POST /guests/lookup`. Сервер сверяет хеш, проверяет статус и блокировку.
3. При успехе киоск показывает «Скидка 10%» и имя гостя в сокращённом виде («Анна К.»), чтобы не раскрывать лишнего человеку у соседнего киоска.
4. Любая попытка пишется в `qr_scan_log`. Много неудачных сканирований подряд с одного киоска временно блокируют сканер.

### 9.4. Правила применения

| Правило | Реализация |
| --- | --- |
| Скидка считается на сервере | Киоск присылает только токен, процент берётся из `guest.discount_percent` |
| Скидка в версии 1 | Процент на весь заказ: `discount_total = round(subtotal * percent / 100)` |
| Один QR не используется в двух заказах | Блокировка `guest_lock`, уникальная для гостя среди активных |
| Блокировка снимается | При отмене, отказе оплаты, тайм-ауте (`released`); при успешной оплате становится `consumed` |
| Баллы начисляются | Только после `approved`, по фактически оплаченной сумме |
| Возврат | Обратная запись `reversal` с `reverses_id`, старая запись не меняется |
| Отзыв QR | Статус `revoked`, перевыпуск создаёт новый токен |

Начисление баллов задаётся настройкой (например, один балл за 100 единиц оплаты). Списание баллов в оплату в версии 1 не входит: скидка даётся процентом, баллы копятся для будущих уровней и акций.

### 9.5. Защита от злоупотреблений

- Скриншот QR можно передать другому человеку. Против этого действуют блокировка одного активного заказа на гостя, журнал сканирований и отчёт для оператора по подозрительным использованиям (например, много заказов за короткое время).
- Если потребуется строже, предусмотрен динамический QR на основе TOTP: приложение или Wallet-карта гостя генерируют код с временем жизни около 30 секунд, а сервер проверяет его локально. Для этого нужно мобильное приложение гостя, поэтому это развитие, а не версия 1.
- Отзыв потерянного кода между синхронизациями не мгновенный. Если ресторан работает без интернета, отзыв применится после следующей синхронизации. Оператор может отозвать код локально сразу.

### 9.6. Персональные данные

- Минимум данных: имя, телефон или почта, дата согласия на обработку (`consent_at`).
- Удаление гостя выполняется анонимизацией (имя и контакты очищаются), а записи `loyalty_tx` и заказов сохраняются без привязки к человеку.
- Требования зависят от страны (GDPR, 152-ФЗ и другие): нужно уточнить юрисдикцию до запуска, включая место хранения данных гостей в облаке.

## 10. Синхронизация с облачным веб-приложением

### 10.1. Что и куда передаётся

| Данные | Источник правды | Направление | Стратегия |
| --- | --- | --- | --- |
| Меню, категории, модификаторы, привязка к станциям | Облако (допущение, см. раздел 18) | Облако в ресторан, правки оператора обратно | Версия записи, побеждает бо́льшая |
| Гости, скидки, статус QR | Облако | Облако в ресторан, новые гости обратно | Версия записи, отзыв QR приоритетен |
| Заказы, строки, задачи | Ресторан | Ресторан в облако | Только добавление |
| Платежи, возвраты | Ресторан | Ресторан в облако | Только добавление, статусы обновляются |
| Журнал баллов `loyalty_tx` | Обе стороны | В обе стороны | Объединение, записи не меняются |
| Устройства, персонал, аудит | Ресторан | Аудит в облако | Только добавление |

### 10.2. Исходящая синхронизация (outbox)

Каждое бизнес-изменение пишет строку в `sync_outbox` в той же транзакции. Фоновый воркер выгружает их в облако:

```python
async def push_loop():
    delay = 5
    while True:
        batch = db.fetch_outbox(limit=100)          # synced_at is null, по возрастанию id
        if not batch:
            await asyncio.sleep(5); continue
        try:
            resp = await cloud.post('/sync/push', events=batch)   # идемпотентно по event id
            db.mark_synced(resp.accepted_ids)
            for rejected in resp.rejected:                       # ошибка данных: не повторять вечно
                db.mark_failed(rejected.id, rejected.reason)
            delay = 5
        except (NetworkError, ServerError):
            await asyncio.sleep(delay)
            delay = min(delay * 2, 300)                          # повтор с нарастающей паузой
```

Облако обязано принимать повторную отправку одного и того же события без побочных эффектов: ключом служат `entity_id` и `id` события. События с ошибкой данных помечаются `failed` и показываются оператору в разделе устройств. Они не блокируют остальную очередь.

### 10.3. Входящая синхронизация

- Сервер периодически (и по сигналу из облака, если доступен канал) вызывает `GET /sync/pull?since=<курсор>&entities=menu,guests`.
- Изменения применяются одной транзакцией по возрастанию версии. Курсор хранится в `sync_state` и сдвигается только после успешного применения.
- Удаления приходят как записи с `deleted_at`, физически строки не удаляются.
- После применения изменений меню сервер рассылает киоскам событие `menu_updated`, и они обновляют кэш Room.

### 10.4. Конфликты

| Ситуация | Правило |
| --- | --- |
| Меню правили в облаке и локально | Побеждает запись с большей `version`; при равенстве, с более поздним `updated_at`; проигравшая сохраняется в `audit_log` |
| Гость изменён с обеих сторон | То же правило, но статус `revoked` не снимается автоматически |
| Два начисления баллов в разных местах | Конфликта нет: записи журнала складываются |
| Заказ уже есть в облаке | Повторная отправка принимается и игнорируется по `id` |

Пока меню имеет два источника правок, возможны потерянные изменения. Поэтому рекомендуется определить одного «главного» редактора меню (см. раздел 18).

### 10.5. Что требуется от облачного API

Контракт нужно уточнить по существующему веб-приложению. Минимальный набор:

- `POST /sync/push`: пакет событий, идемпотентный приём, ответ со списком принятых и отклонённых;
- `GET /sync/pull`: изменения по курсору с постраничной выдачей;
- аутентификация по токену ресторана (ключ на сервер, не на планшет), по возможности с ограничением по IP или mTLS;
- версионирование API и схемы событий, чтобы обновления сервера и облака не требовали одновременного выпуска;
- идентификатор ресторана (`restaurant_id`) во всех событиях.

### 10.6. Поведение без интернета

Очередь `sync_outbox` растёт и выгружается после восстановления связи. Меню и гости актуальны на момент последней синхронизации. В разделе оператора показывается время последней успешной синхронизации и размер очереди, а если связи нет дольше заданного времени (например, 2 часа), появляется предупреждение. На работу киосков и станций это не влияет.

## 11. API локального сервера

### 11.1. Общие правила

- REST поверх HTTPS, JSON, префикс `/api/v1`. Документация OpenAPI генерируется FastAPI автоматически.
- Авторизация: заголовок `Authorization: Bearer <токен устройства>`. Для действий оператора добавляется токен сотрудника, полученный по PIN.
- Все запросы, создающие или меняющие данные, принимают `Idempotency-Key` (UUID). Повтор с тем же ключом возвращает сохранённый ответ.
- Время: ISO 8601, UTC. Суммы: целые числа в минимальных единицах валюты.
- Ошибки в едином формате: `{"error": {"code": "item_unavailable", "message": "...", "details": {}}}`.

## 12. Безопасность

### 12.1. Устройства

- Новое устройство регистрируется одноразовым кодом, который выдаёт оператор. В ответ устройство получает длинный случайный токен и хранит его в Android Keystore. Сервер хранит только хеш.
- Устройство можно отключить из панели оператора, токен перестаёт работать сразу.
- Киоск работает в режиме Device Owner с Lock Task Mode, отключёнными USB-отладкой и доступом к настройкам. Физически планшет закреплён.

### 12.2. Персонал

- Вход по PIN (не короче 6 цифр), хранится только хеш (Argon2). После 5 неудачных попыток вход блокируется на 5 минут.
- Токен сотрудника живёт 15 минут и продлевается при активности.
- Для опасных действий (возврат, ручное решение по платежу, смена скидки гостя) PIN запрашивается повторно.

### 12.4. Транспорт и данные

- Внутри локальной сети используется TLS. Сертификаты выпускает собственный центр сертификации ресторана, клиент проверяет сервер по закреплённому сертификату (pinning).
- Связь с облаком идёт по HTTPS с токеном ресторана, который хранится только на сервере.
- Данные банковских карт в системе не присутствуют. Платёжный терминал сертифицирован отдельно и остаётся в зоне ответственности банка и производителя. Это снижает объём требований PCI DSS, но точный уровень нужно подтвердить с банком-эквайером.
- Диск сервера и резервные копии шифруются. В логах нет токенов, PIN и полных данных гостей.

### 12.5. Доверие к клиенту

Сервер не доверяет клиенту ни в чём, что влияет на деньги или статусы: цены, скидка, состав и время готовности считаются на сервере; смена статуса задачи принимается только от устройства своей станции; число запросов на устройство ограничено.

## 13. Отказоустойчивость и сценарии сбоев

| Сбой | Что происходит | Реакция системы |
| --- | --- | --- |
| Пропал интернет ресторана | Локальная сеть работает | Заказы и оплата идут как обычно (терминал использует свой канал), `sync_outbox` накапливается |
| У терминала нет связи с банком | Оплата невозможна | Киоск показывает «Оплата временно недоступна», оператору приходит предупреждение, новые заказы не принимаются |
| Команда не дошла до терминала | Деньги не списаны | Платёж закрывается как `cancelled` с кодом `terminal_unreachable`, гость может повторить |
| Команда отправлена, ответа нет | Результат неизвестен | Запрос статуса по `reference`, затем `unknown` и ручной разбор (раздел 8.4) |
| Киоск завис или перезагрузился | Сессия потеряна | Сервер доводит платёж до конца сам. Новый гость начинает заново, оплаченный заказ уже в работе |
| Станция потеряла Wi-Fi | Нет новых задач | Красная плашка «нет связи». Нажатия «Начал» и «Готово» сохраняются на планшете и отправляются после восстановления, сервер принимает их идемпотентно |
| Перезапуск сервера | Соединения оборваны | Автозапуск службы, состояние берётся из БД, слоты планировщика восстанавливаются, клиенты переподключаются сами |
| Отключение питания | Возможны незавершённые операции | ИБП на сервере и роутере. При старте проверка целостности БД, платежи в `in_progress` сверяются с терминалом |
| Повреждение диска или базы | Данные недоступны | Восстановление из последней копии, недостающие записи сверяются с облаком и отчётом терминала |
| Облако недоступно | Синхронизация встаёт | Ресторан не затронут, повторные попытки с нарастающей паузой, предупреждение при долгом простое |

Важно различать два случая: «команда на терминал не ушла» (повторить безопасно) и «команда ушла, ответа нет» (повторять нельзя). Адаптер терминала обязан возвращать эту разницу явно.

## 14. Развёртывание и эксплуатация

### 14.1. Оборудование (ориентировочно)

| Что | Рекомендация |
| --- | --- |
| Сервер | Мини-ПК или Raspberry Pi 5, 8 ГБ ОЗУ, SSD (не SD-карта) |
| Питание | ИБП на сервер, роутер и коммутатор |
| Сеть | Роутер и PoE-коммутатор, киоски по Ethernet, станции и выдача по Wi-Fi |
| Киоски | Планшеты 10 дюймов и больше с поддержкой Android Enterprise, антивандальные стойки |
| Станции | Влагозащищённые планшеты или мониторы на Android, крепление на уровне глаз |
| Выдача | Android-телевизор или планшет, динамик |
| Терминал | С локальным API и собственным каналом к банку |
| Принтер | Чековый, по требованиям раздела 8.7 |

### 14.2. Окружение сервера

- Debian или Ubuntu Server LTS. Приложение запускается как служба (`systemd` с `Restart=always`) или как контейнер Docker Compose. Выбор делается один раз и фиксируется в репозитории.
- Python 3.12, `uvicorn` за обратным прокси (Caddy или nginx), который держит TLS.
- Синхронизация времени (`chrony`). Без интернета время может уходить, поэтому в сервере нужны аппаратные часы, а при наличии, локальный NTP на роутере. Время критично для таймеров станций, поэтому клиенты ориентируются на время сервера, а не на собственные часы.
- Ротация логов и контроль свободного места на диске.

### 14.3. Обновления

- Сервер собирается в CI. Обновление выполняется вне часов работы, перед ним автоматически делается копия базы, откат возвращает предыдущую версию и копию.
- Android-приложение распространяется через MDM или управляемый Google Play, обновляется в нерабочее время.
- Сервер поддерживает предыдущую версию API клиентов, чтобы обновление планшетов не пришлось делать одновременно.

### 14.4. Мониторинг

| Показатель | Порог для предупреждения |
| --- | --- |
| Платежи в статусе `unknown` | Любой |
| Возраст последней успешной синхронизации | Более 2 часов |
| Размер очереди `sync_outbox` | Растёт без разгрузки |
| Устройства без связи | Станция или киоск более 2 минут |
| Ошибки терминала | Подряд 3 и более |
| Свободное место на диске | Меньше 20% |
| Задержка от `approved` до появления задачи на станции | Больше 1 секунды |

Предупреждения показываются в панели оператора. Если есть интернет, владелец получает уведомление через облачное приложение. Логи пишутся в структурированном виде (JSON) с идентификатором заказа и платежа.

### 14.5. Регламент смены

- **Открытие:** проверить, что все устройства в сети, терминал отвечает, меню актуально, принтер заряжен бумагой.
- **В течение дня:** оператор следит за очередью `unknown` и предупреждениями.
- **Закрытие:** закрыть смену на терминале, посмотреть сверку, убедиться, что синхронизация догнала очередь или предупреждение зафиксировано.

## 15. Тестирование

| Уровень | Что проверяется |
| --- | --- |
| Модульные | Планировщик (все задачи заканчиваются одновременно, слоты не пересекаются), скидки и округление, автоматы статусов |
| Интеграционные | Заказ, оплата через `MockTerminal`, создание задач, идемпотентные повторы, гонка двух киосков за один QR |
| Сценарии сбоев | Тайм-аут терминала, обрыв после `sale`, двойной ответ, отказ, перезапуск сервера посреди платежа |
| Синхронизация | Повтор пакета, обрыв посреди отправки, конфликт версий, очередь в тысячи событий |
| Нагрузка | 6 киосков, 60 заказов в час, всплеск в 10 раз, задержка событий меньше 1 секунды |
| Android | UI-тесты Compose, режим киоска на реальном планшете, QR при разном освещении и с разных экранов, потеря и возврат Wi-Fi |
| Приёмка терминала | Чек-лист эквайера: оплата, отказ, отмена, возврат, закрытие смены, обрыв связи |
| Пилот | Неделя работы параллельно с обычной кассой |

Главное правило: всё, что касается денег и статусов, покрывается автоматическими тестами раньше, чем получает интерфейс.

## 16. План разработки

Сроки не указаны: их можно оценить после этапа 0, когда будут известны терминал, API веб-приложения и состав команды.

| Этап | Содержание | Результат |
| --- | --- | --- |
| 0. Подготовка | Выбор терминала, изучение веб-приложения, ответы на вопросы раздела 18, макеты экранов | Утверждённые требования |
| 1. Каркас | Сервер, БД, миграции, регистрация устройств, чтение меню, `MockTerminal` | Работающий сервер и пустые клиенты |
| 2. Заказ и оплата | Киоск от меню до оплаты, статусы заказа и платежа, идемпотентность | Гость заказывает и платит (на имитаторе) |
| 3. Станции | `station_task`, планировщик, экран станции и выдачи, WebSocket | Заказ доходит до станций и выдачи |
| 4. Оператор | CRUD меню и привязок, очередь `unknown`, возвраты, устройства | Ресторан управляется без разработчика |
| 5. Лояльность | Гости, QR, скидки, журнал баллов, блокировки | Скидка по QR |
| 6. Реальный терминал | Адаптер, чек-лист эквайера, закрытие смены, чеки | Настоящие платежи |
| 7. Синхронизация | Outbox, pull, конфликты, мониторинг | Связь с веб-приложением |
| 8. Надёжность и пилот | Нагрузка, сбои, обучение персонала, пилот | Запуск |

Этапы 2 и 3 можно вести параллельно: серверную и клиентскую части. Этап 6 лучше начинать, как только есть доступ к терминалу, а не после этапа 5, чтобы ограничения терминала не вскрылись поздно.

## 17. Риски

| Риск | Меры |
| --- | --- |
| Выбранный терминал без локального API или без запроса статуса | Выбрать терминал до этапа 2, требования в разделе 8.1, пока работать на `MockTerminal` |
| Неопределённые платежи | Процедура 8.4, очередь у оператора, обучение персонала |
| Потеря данных при отключении питания или отказе диска | ИБП, WAL с `synchronous=FULL`, почасовые копии, сверка с терминалом и облаком |
| Конфликты правок меню в двух местах | Один главный редактор меню, версии записей, аудит |
| Злоупотребление чужим QR | Блокировка одного заказа, журнал сканирований, при необходимости TOTP |
| Нестабильный Wi-Fi в зале | Ethernet для киосков, очередь действий на станциях, мониторинг связи |
| Уход времени без интернета | Аппаратные часы, локальный NTP, серверное время для таймеров |
| Фискализация и персональные данные | Уточнить страну до этапа 6, интерфейс `ReceiptService`, согласия гостей |
| Выход гостя из режима киоска | Device Owner, Lock Task Mode, физическое крепление |
| Сложность поддержки без разработчика на месте | Удалённый доступ, мониторинг, регламент смены |
